Self-correcting Code-adaptive DevOps Agent

I built a self-correcting code-adaptive DevOps Agent that takes in Resource Provider (RP) specific files, generates output code, attempts to build the project, feeds build errors back to the model until errors are fixed, and finally pushes code to Azure DevOps with an automated PR.

UI Development & User Experience

The UI was built using Streamlit for a lightweight framework as the work was LLM-heavy. The design evolved from a simple chatbot to include:

  • Text boxes and checkboxes to select files needed for uploading into LLM memory
  • Real-time display of generated code on the UI
  • Build error visualization and tracking
  • Pipeline re-running interface with build error feedback
  • Corrected code regeneration display
  • PR creation button with final PR link display

Technical Architecture & Azure Integration

The project began with exploring Azure services and deciding to use Azure Foundry SDK to handle tools, webhooks, and integrations. While a simple RAG pipeline using the SDK worked initially, the code quality wasn't sufficient and executed with build errors. This led to implementing three major improvements:

1. Extensive Prompt Engineering

  • Developed sophisticated prompt engineering strategies with few-shot examples of specific code patterns
  • Helped generate the correct skeleton and structure of the code
  • Significantly improved initial code generation quality

2. Metadata-Based Code-Adaptive RAG Approach (Key Innovation)

Problem: Initially, single files were uploaded to the vector database and retrieved based on highest match to new RP descriptions. This caused significant information mismatches and incomplete project context.

Solution: I invented a metadata-based approach to retrieve relevant projects as complete units:

  • Created metadata structure containing: project name, RP description and functionality, and names of all files present in the RP
  • Only the description was embedded in the vector database, not individual files
  • For incoming new RP requests, the new description was embedded and matched against existing RP descriptions
  • Most similar RPs were retrieved as whole projects rather than individual files
  • This approach made the RAG pipeline code-adaptive rather than just text-adaptive
  • Significantly improved performance by maintaining project structure and context

3. Self-Correcting Build Automation (Major Breakthrough)

Challenge: We were manually building projects and feeding errors back, a time-consuming and inefficient process.

Innovation: Automated the entire build-fix-rebuild cycle:

  • Wrote a script to automatically build the project after code generation
  • Captured build errors and fed them back to the LLM automatically
  • Provided new instructions along with build errors to guide regeneration
  • LLM regenerated the entire codebase with corrections
  • Loop continued until the build was successful
  • Result: Improved code writing time by 75%

Key Impact & Results

  • 75% improvement in code generation accuracy and development time
  • Reduced manual intervention through automated build-fix cycles
  • Invented metadata-based code-adaptive RAG approach for maintaining project context
  • Successfully integrated with Azure DevOps for automated PR creation

AgentOS: An Ambient AI Agent for Career & Wellbeing

Personal Project

Multi-Agent System | Google ADK, Gemini, Google Cloud Run

The Problem

A serious job search has a way of quietly eating everything else in your life. Interviews get scheduled over lunch, focus time disappears the moment a recruiter calls, and your inbox turns into a second job. I built AgentOS to sit in the background and actually protect the parts of my day a calendar app alone won't defend.

What It Does

  • Watches your calendar and keeps wellness blocks (focus time, meals, workouts) from being quietly cannibalized by interview requests
  • Triages your inbox so the threads that actually matter surface first
  • Uses Gemini to reason about where a bumped task should go next, instead of falling back on a rigid, hardcoded rule

Why Multi-Agent

Calendar logic, inbox triage, and rescheduling all need different context and different guardrails, so cramming it all into one prompt gets messy fast. AgentOS splits the problem across a set of cooperating agents, each responsible for one slice of it, coordinated through a custom ADK-style runtime rather than one do-everything model call.

Built Like Production Software

Since it touches a real calendar and a real inbox, it's engineered accordingly, not thrown together as a demo:

  • OAuth sessions backed by Firestore, so a login actually persists
  • AES-256-GCM encryption at rest for anything sensitive it stores
  • A full CI/CD pipeline that redeploys to Google Cloud Run on every change
  • A React front end talking to a Node.js/Express backend over a clean API boundary

Fleet Triage: GPU Cluster Failure Diagnosis

Personal Project

RAG + Knowledge Graph Pipeline | FastAPI, Next.js, Neo4j, AWS

An evidence-backed triage agent for GPU training clusters. It tells engineers what failed, why it failed, and whether to pull the node.

Measured Impact

  • 95.8% verdict accuracy, up from 0% without evidence
  • 100% drain-decision accuracy, up from 70.8%
  • 110x lower cost per decision
  • 13x faster decisions, about 4s down to about 300ms

The Problem

At fleet scale, GPU failures happen all the time. Meta reported about one GPU-related interruption every three hours while training Llama 3 405B on 16,384 GPUs. Each failure forces a fast call: is this a documented known issue? Is it a new failure worth escalating, a bug in the workload, or just an artifact of the test setup?

Get it wrong and you either drain a healthy node for nothing or leave a bad one burning compute. Fleet Triage takes a failure report and returns a typed, evidence-backed answer instead of a guess.

The Pipeline

Every triage runs through four stages. Each one checkpoints before the next starts, so an interrupted run picks up where it stopped instead of starting over.

  • Retrieval: dense vector search and BM25 run side by side, their results fused by rank and then reranked by a cross encoder
  • Graph: entities from the report are matched in a Neo4j knowledge graph and walked out two hops
  • Decision: Jev returns a typed verdict, a probability that the node should be drained, and a severity score
  • Synthesis: a plain-English explanation is written using only the evidence gathered above

Two Search Methods, One Ranked List

Vector search catches meaning. BM25 catches exact terms like error codes and driver versions. Fleet Triage runs both and merges them with Reciprocal Rank Fusion.

It fuses by rank, not by score, because the two scores sit on different scales. Forcing them onto one range would push the weaker signal to zero, and a real match would then look the same as no match at all.

Cross Encoder Reranking

Fusion gives a strong shortlist. The cross encoder makes the final call: it reads the failure report and each candidate together, so it judges how relevant they really are to each other, not just how similar they look.

Its scores mean the same thing across every query, so the relevance threshold lives here. When nothing relevant exists, the system returns no context rather than falling back on the least-bad chunks. The final set also keeps one chunk per source document, so one long writeup can't crowd out everything else.

Graph Retrieval

Search finds similar incidents. The graph finds connected facts. Triples are pulled from every document and merged into Neo4j on entity name.

Generic words like "node" would turn into hubs linking hundreds of unrelated records, so entities above a degree cap, plus a blocklist of generic nouns, are left out of both matching and traversal. This keeps every hop meaningful.

From Error Code to Resolution

Two hops is enough for an error code to reach the component it affects and the fix on record for it:

out of bounds access → custom kernel → xid 13
xid 48 → double bit ECC error → RMA

The decision stage gets both views together, ranked incident evidence from retrieval and linked facts from the graph, so the verdict knows what happened before and also what to do about it.

Structured Decisions with Jev

The verdict is not free text. It comes from Jev, a typed decision model, through OpenRouter.

  • Structured: the verdict is a fixed choice (known issue, new issue, user code, or test artifact), the drain decision is a real probability, and severity follows an ordered rubric. There is no prose to parse and no broken JSON to catch downstream
  • Grounded: Jev only sees the evidence and graph facts gathered for this run, which is why accuracy climbs from 0% to 95.8% once evidence is added
  • Fast: a decision takes about 300ms, compared with about 4s through a general-purpose chat model
  • Cheap: it's billed per classification, not per token generated, which makes it about 110x cheaper, and that matters when failures come in by the thousands

The decision runs before synthesis, since it doesn't need the model that writes the explanation. If no Jev key is set, a chat model with a checked JSON contract takes over.

Results

  • Verdict accuracy: 0% to 95.8% once retrieval and graph evidence are added
  • Drain accuracy: 70.8% to 100%, so no healthy node gets pulled and no failing one stays in service
  • Cost and speed: 110x cheaper and 13x faster than routing the same decision through a general-purpose chat model
  • Infrastructure: profiling showed the graph database was allocated 780MB but held only 65MB of data, so moving to managed AuraDB avoided a compute upgrade that wasn't needed

Built for Operations

  • A full audit trail for every run, so any decision can be traced after the fact
  • Live streaming of each stage as it finishes, so engineers see evidence before the verdict lands
  • Runs resume from their last checkpoint
  • If the model can't be reached, the API returns an error instead of a made-up answer

Hard Cases It Has to Call

The system is tested on the failures that trip up engineers the most:

  • Xid 13 and Xid 31 errors look like hardware faults but come from the workload
  • Xid 43 could be a long-running kernel or a device that stopped responding
  • NCCL timeouts look the same whether the cause is a fabric fault or one slow rank
  • Host out-of-memory kills the job with no GPU error at all

Deployment & Security

  • The backend runs on EC2 and can only be reached through CloudFront, with a custom origin header checked on every request
  • There is no SSH key and no open management port, access goes through SSM Session Manager and is authenticated by IAM
  • The knowledge graph runs on Neo4j AuraDB instead of a self-hosted container
  • The frontend is served from S3 through its own CloudFront distribution, separate from the API
  • A daily run cap, a per-caller rate limit, and a query length limit protect the public endpoint
  • Every push to main builds the image, pushes it to ECR, and redeploys over SSM, all through GitHub OIDC rather than a stored AWS key
